## 4. PHASE B — TRACEFIX-INTEGRATION

### 4.1 Die TraceFix-Methodik (online-validiert)

**TraceFix** (ACM CAIS 2026, Best Paper Award, Rutgers University) ist eine verification-first pipeline für LLM Multi-Agent Coordination. Der Kern:

- Ein Agent synthetisiert eine Protokoll-Topologie als strukturierte Zwischendarstellung (IR)
- Generiert PlusCal-Koordinationslogik
- **Repariert das Protokoll iterativ mit Counterexamples aus dem TLA+ Model Checker (TLC), bis die Verifikation erfolgreich ist**
- Auf 48 Tasks über 16 Szenario-Familien: **Alle Tasks erreichen volle TLC-Verifikation; 62,5% bestehen beim ersten Versuch, keiner braucht mehr als vier Reparatur-Iterationen**
- **TLC-verifizierte Protokolle reduzieren Deadlock/Livelock von 31,1% auf 14,1%**

**Open Source:** `github.com/ModelWisdom/ModelWisdom` bietet **ModelRepair** — extrahiert Fehlerinformationen aus TLC und nutzt LLMs zur Reparatur.

### 4.2 MANUS-Auftrag

```text
SCHRITT_B1: TRACEFIX-KONZEPT AUF R36-COUNTEREXAMPLE ANWENDEN

  → Der R36-Counterexample (InvW1_2 verletzt) ist der Input.
  → TraceFix-Loop (manuell, nicht automatisiert):
      1. Counterexample analysieren
      2. Reparaturvorschlag generieren (A/B/C)
      3. TLC erneut ausführen
      4. Falls PASS: Loop beenden
      5. Falls COUNTEREXAMPLE: neuen Vorschlag generieren
  → Ziel: Zeigen, dass der TraceFix-Ansatz auf NEXUS anwendbar ist.

SCHRITT_B2: MODELWISDOM EVALUIEREN

  → Öffne github.com/ModelWisdom/ModelWisdom
  → Prüfe: Ist das Tool installierbar?
  → Prüfe: Kann es den R36-Counterexample analysieren?
  → Dokumentiere: Funktioniert es? Wo sind Grenzen?

SCHRITT_B3: EMPFEHLUNG

  → Soll TraceFix in NEXUS integriert werden?
  → Soll ModelWisdom als Tool verwendet werden?
  → Welche Voraussetzungen fehlen?
```

**Output:** `R41_PHASE_B_TRACEFIX_INTEGRATION_REPORT.md` + `R41_PHASE_B_MODELWISDOM_EVALUATION.json`

**Forschungsanker:** TraceFix zeigt, dass die Kombination aus TLA+, Counterexamples und LLM-basierter Reparatur eine signifikante Verbesserung bringt: 62,5% First-Try-Erfolg, max. 4 Iterationen, Deadlock-Reduktion um 17 Prozentpunkte. ModelWisdom bietet die konkrete Tool-Implementierung.

## 5. PHASE C — APALACHE-SYMBOLIC-VERIFICATION

### 5.1 Die Apalache-Engine (online-validiert)

**Apalache** (CAV 2026) ist ein symbolischer SMT-basierter Model Checker für TLA+. Der Kern:

- Übersetzt TLA+ in SMT-Logik (Microsoft Z3, CVC5)
- **Drei komplementäre Funktionalitäten:**
  - Bounded exhaustive verification (für beschränkte Garantien)
  - Randomised symbolic execution (für Prototyping und Bug-Detection)
  - **Inductiveness checking (für unbeschränkte Garantien)**
- **Kann induktive Invarianten prüfen** (`Init => Inv, Inv /\ Next => Inv'`) für feste oder beschränkte Parameter
- **Kann Fairness-Bedingungen nicht direkt prüfen** — TLC kann das

**Docker:** `ghcr.io/apalache-mc/apalache:main` — Apache 2.0

  → Docker-Image pullen: ghcr.io/apalache-mc/apalache:main

**Forschungsanker:** Die TLA+-Trifecta-Publikation beschreibt: „Apalache is particularly useful when it comes to checking inductive invariants". Apalache kann **Fairness-Bedingungen nicht direkt prüfen** — das ist eine echte Grenze.

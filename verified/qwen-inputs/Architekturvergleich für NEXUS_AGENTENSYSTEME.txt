Architekturvergleich QWEN:

# Architekturvergleich für fälschungssichere Agentensysteme: Eine tiefgehende Validierung von GitLab/Duo/MCP/Orbit versus AXIOM/Cursor/GitHub anhand der Claim-Kette

## Fundamentale Architekturvergleiche: GitLab/Duo/MCP/Orbit versus AXIOM/Cursor/GitHub

Die vorliegende Untersuchung vergleicht zwei komplexe Architekturgruppen im Kontext ihrer Fähigkeit, eine stringent definierte Claim-Kette zu validieren. Diese Kette dient als primäres Gate zur Sicherstellung der Integrität, Nachverfolgbarkeit und Vertrauenswürdigkeit agenter Systeme. Die erste Architekturgruppe, bezeichnet als „GitLab-Duo-MCP“, kombiniert die DevOps-Plattform GitLab mit dessen künstlicher Intelligenz-Agenten-Plattform Duo, dem Model Context Protocol (MCP) zur Integration externer Werkzeuge und dem organisatorischen Framework Orbit [[108]]. Die zweite Gruppe, „AXIOM-Cursor-GitHub“, setzt auf die Synergie zwischen dem Datenanalyse-Plattform Axiom, der künstlich-intelligenten IDE Cursor und der Code-Hosting-Plattform GitHub. Der Analyse liegt eine strikte Priorisierung zugrunde: Zuerst sind acht spezifische Forschungsfährten mit höchster Dringlichkeit abzuarbeiten, bevor definitive positive Bewertungen vergeben werden dürfen [[1]]. Diese PO-Fährten umfassen die Bereiche Tool Governance, Runner/Sandbox, Composite Identity, Security Policy Project, Pipeline Execution Policies, bidirektionales MCP, Provenienz/Beweise und Blindvalidierung [[1]]. Die Bewertung der Architekturen erfolgt nicht durch abschließende Urteile wie „sicher“ oder „unabhängig“, sondern durch eine detaillierte Auswertung der Erfüllung formaler Kriterien für jedes Glied der Claim-Kette, unterstützt durch Vektormetriken zur quantitativen Beschreibung der Stärken und Schwächen jeder Architektur <user>. Jede Behauptung wird aktiv auf potenzielle Umgehungspfade hin überprüft, um die Robustheit der Architekturen zu testen <user>. Die Analyse beschränkt sich bewusst auf die Untersuchung der vorhandenen Mechanismen und deren Dokumentation, ohne direkte Eingriffe oder Konfigurationsänderungen vorzunehmen <user>.

Die Architektur GitLab-Duo-MCP repräsentiert einen traditionelleren Ansatz, der auf einer etablierten CI/CD-Plattform aufbaut und diese durch künstliche Intelligenz-gestützte Komponenten erweitert. GitLab selbst bietet mächtige Werkzeuge für die Infrastruktur- und Codeverwaltung, einschließlich eines offenen Source-Code-Projekts namens GitLab Runner, das für die Ausführung von CI/CD-Jobs verantwortlich ist [[69,75]]. Die Integration von Duo zielt darauf ab, die Sicherheit und Identitätsverwaltung durch Funktionen wie Zweifaktor-Authentifizierung (MFA) und die Erstellung einer „Composite Identity“ zu stärken [[29,205]]. Die Rolle des Model Context Protocols (MCP) innerhalb dieser Architektur scheint vor allem darauf abzuzielen, die GitLab-Umgebung für externe Agenten und LLMs nutzbar zu machen, indem es eine Schnittstelle bereitstellt [[339,496]]. Das Framework Orbit fungiert hier als übergeordnetes Konzept zur Förderung organisationaler Kohärenz und Kulturentwicklung, was jedoch weniger technisch-definiert ist und eher auf Management-Standards zurückgreift [[370,371]]. Ein wesentlicher Aspekt dieser Architektur ist die enge Kopplung aller Komponenten. Die Kommunikation zwischen GitLab und Duo läuft über den GitLab-Server selbst, was eine hohe Interoperabilität impliziert, aber auch eine potenzielle Single-Point-of-Failure darstellt [[28]].

Im Gegensatz dazu positioniert sich die Architektur AXIOM-Cursor-GitHub als moderneres, protokollzentriertes Ökosystem, das explizit auf die Herausforderungen agenter Systeme ausgelegt ist. Hier agiert Axiom nicht nur als Datenquelle, sondern auch als Adjudikationsmechanismus, der durch seinen MCP-Server eine standardisierte Schnittstelle für Agenten bereitstellt, um nachrichtenartig auf Daten zu zugreifen [[292,294]]. Cursor fungiert als primärer MCP-Client, ein intelligentes Entwicklungs-Environments, das in der Lage ist, Aufgaben autonom zu planen und auszuführen [[152,319]]. GitHub bildet die Grundlage für Code, Artefakte und Provenienz und stellt moderne Authentifizierungsmechanismen wie OpenID Connect (OIDC) zur Verfügung [[207,208]]. Dies ermöglicht eine sehr starke, kryptografisch gesicherte Bindung von Aktionen an identifizierte Benutzer. Die Komponenten dieser Architektur sind modularer und kommunizieren über offene Standards wie MCP und OIDC, was eine höhere Flexibilität und potenziell bessere Trennung der Zuständigkeiten verspricht. Beispielsweise kann ein Agent in Cursor direkt mit einem MCP-Server von Axiom verbunden sein, während gleichzeitig seine Aktionen in GitHub über OIDC-Tokens mit immutablen Subjekt-Ansprüchen protokolliert werden [[163]]. Dies schafft ein robustes Gerüst für die Generierung von Beweisen (`RECEIPT-VERIFIED`). Während die GitLab-Architektur eine monolithische Einheit darstellt, bei der die Komponenten eng miteinander verwoben sind, strebt die GitHub-Architektur eine dezentralisierte, aber gut koordinierte Interoperabilität an, die auf Industriestandards basiert. Diese grundlegende philosophische Differenz zwischen enger Integration und offener Standardisierung prägt die gesamte Analyse und wird sich bei der Prüfung jeder Phase der Claim-Kette manifestieren.

| Merkmal | Architektur A: GitLab-Duo-MCP | Architektur B: AXIOM-Cursor-GitHub |
| :--- | :--- | :--- |
| **Dominierendes Paradigma** | Integrated DevSecOps Platform with AI augmentation [[265]] | Modular, protocol-driven Agentic Ecosystem [[212]] |
| **Identitätsmanagement** | Composite Identity via GitLab Duo [[205]], SAML/OIDC support [[209]] | Strong identity binding via OIDC with immutable subject claims [[163]] |
| **Agenten-Ausführungsumgebung** | Self-hosted or Hosted Runners [[236]] | AI IDE Sandboxing [[395]], Headless CLI for automation [[144]] |
| **Werkzeugintegration (MCP)** | Primarily as a client-facing interface [[339]] | Native client (Cursor) and server (Axiom) implementation [[292]] |
| **Provenienz & Beweise** | Indirectly via SLSA concepts through runners [[137]] | Directly via OIDC tokens with cryptographically verifiable claims [[163]] |
| **Governance & Rules** | Config-as-Code policies [[142]], Scan execution policies [[74]] | Cursor's internal rules engine [[255]], GitHub Enterprise policies [[12]] |
| **Adjudikation** | Not natively integrated; requires external logic [[19]] | Natively supported via Axiom MCP Server [[292]] |
| **Architektonischer Ansatz** | Tight coupling within a single vendor ecosystem [[28]] | Loose coupling via open protocols (MCP, OIDC) [[242]] |

## Validierung der Claim-Kette: EXISTENZ bis FREIGEGEBEN

Die erste Sequenz der Claim-Kette – `EXISTS`, `ENTITLED`, `ENABLED` und `CONFIGURED` – legt die grundlegenden Voraussetzungen für die Existenz und Funktionsfähigkeit eines Systems fest. Diese Phasen prüfen, ob die Architekturen existieren, welche Berechtigungen ihnen zugeordnet sind, ob sie aktiviert werden können und ob eine funktionale Konfiguration möglich ist. Die Analyse dieser Glieder zeigt deutliche Unterschiede in der Herangehensweise und der Robustheit der jeweiligen Architekturen. Die Anforderung lautet, für jedes Glied einen positiven Nachweis, einen negativen Testfall, eine Blindstelle und eine Abbruchbedingung anzugeben [[1]].

**`EXISTS`:** Beide Architekturgruppen bestehen uneingeschränkt. GitLab ist eine weit verbreitete, kommerziell verfügbare Plattform für CI/CD und DevOps [[69]]. Duo ist ein etablierter Anbieter für MFA-Lösungen, der nahtlos in GitLab integriert werden kann [[29]]. Orbit wird als Rahmenwerk für Organisationen beschrieben, das kulturelle und operative Kohärenz fördert [[108]]. Auf der anderen Seite existiert Axiom als Datenanalyse-Plattform, Cursor als AI-fähiges IDE-Ökosystem und GitHub als dominierender Code-Hosting-Dienst [[3,146,296]]. **Positive Nachweis:** Die kommerzielle Verfügbarkeit und Dokumentation dieser Produkte in den Quellen belegt ihre Existenz. **Negative Testfälle:** Es gibt keine Hinweise darauf, dass diese Plattformen nicht existieren oder nicht verfügbar wären. **Blindstellen:** Die langfristige strategische Stabilität oder der Support für alle einzelnen Komponenten innerhalb der Gruppen könnte eine Blindstelle darstellen, da dies aus den bereitgestellten Materialien nicht vollständig ersichtlich ist. **Abbruchbedingung:** Die Nichtverfügbarkeit eines zentralen Dienstes innerhalb einer Gruppe würde die Existenz der gesamten Architektur gefährden, was jedoch ein Betriebsproblem und kein Designfehler ist.

**`ENTITLED`:** Dieses Glied prüft, ob den beteiligten Akteuren (Benutzer, Gruppen, Agenten) klar definierte Rechte und Rollen zugewiesen werden können. **Architektur A (GitLab-Duo-MCP):** GitLab bietet ein reichhaltiges Role-Based Access Control (RBAC) Modell, das auf Projekte, Gruppen und Instanzebene konfiguriert werden kann [[36,501]]. Durch die Integration von Duo können zusätzliche Bedingungen an die Berechtigung angehängt werden, beispielsweise eine erfolgreiche Zwei-Faktor-Authentifizierung [[30]]. Die Möglichkeit, bestimmte Projekte für Instanz-Runner zu begrenzen, demonstriert eine granulare Steuerung [[501]]. **Positive Nachweis:** Die Konfiguration von Projektbesitzern, Maintainern und anderen Rollen in GitLab ist dokumentiert . **Negative Testfall:** Ein Benutzer ohne ausreichende Berechtigung kann beispielsweise keine Pipelines starten oder Konfigurationen ändern. **Blindstelle:** Die Komplexität der RBAC-Regeln kann zu Konflikten oder unbeabsichtigtem Zugriff führen. Insbesondere die Wechselwirkung zwischen GitLab-Rollen und Duo-basierten Policies ist eine potenzielle Quelle für Missverständnisse und Fehler [[389]]. **Abbruchbedingung:** Ein Administrator könnte sich weigern, Berechtigungen zu erteilen, was die Weiterarbeit blockiert. **Architektur B (AXIOM-Cursor-GitHub):** Auch hier sind starke Mechanismen vorhanden. GitHub verwendet ein RBAC-Modell, das auf Organisationen und Repositories basiert [[12]]. Mit Hilfe von SAML SSO und SCIM kann die Identitätsverwaltung und damit die Zuweisung von Berechtigungen zentralisiert werden [[54,55]]. Cursor ermöglicht ebenfalls die Definition von Regeln, die das Verhalten von Agenten steuern, was eine Form von policy-basiertem Entitlement darstellt [[255]]. **Positive Nachweis:** Die Zuweisung von Admin-Rechten in einer GitHub-Organisation oder die Konfiguration von Cursor-Rules zur Steuerung von Code-Änderungen. **Negative Testfall:** Ein Agent, der keine Berechtigung zum Pushen in eine geschützte Branch hat, wird vom Versuch blockiert. **Blindstelle:** Die Abhängigkeit von SCIM für die Benutzerbereitstellung bedeutet, dass fehlgeschlagene Provisioning-Vorgänge zu inkonsistenten Berechtigungen führen können [[46]]. **Abbruchbedingung:** Ein fehlgeschlagener Login-Versuch aufgrund ungültiger Anmeldeinformationen.

**`ENABLED`:** Dieses Glied überprüft, ob die Architekturen aktiviert und ihre Kernfunktionen initialisiert werden können. **Architektur A:** Die Aktivierung von GitLab-Duo erfordert eine korrekte Lizenzierung, die Konfiguration von API-Schlüsseln und die Einhaltung spezifischer Voraussetzungen, wie etwa das Deaktivieren der Duo-Einstellung auf Instanzebene, um die Composite Identity zu aktivieren – ein Widerspruch, der zu Fehlschlägen führen kann [[206,223]]. Die Aktivierung von CI/CD-Pipelines hängt von der korrekten Konfiguration von Runnern ab [[76]]. **Positive Nachweis:** Nach erfolgreicher Konfiguration in den GitLab-Einstellungen wird die Duo-Funktionalität aktiviert [[451]]. **Negative Testfall:** Ein Administrator versucht, die Composite Identity zu aktivieren, erhält aber die Fehlermeldung, dass die Duo-Einstellung auf Instanzebene deaktiviert ist, was den Prozess blockiert [[206]]. **Blindstelle:** Die Abhängigkeit von der Reihenfolge der Konfigurationsschritte (z.B. erst Lizenz prüfen, dann Duo aktivieren, dann Composite Identity) ist eine bekannte Schwachstelle [[223,225]]. **Abbruchbedingung:** Das Fehlen einer gültigen Lizenz für GitLab Ultimate oder Duo würde die Aktivierung funktionaler Komponenten unmöglich machen [[414]]. **Architektur B:** Die Aktivierung ist ebenfalls abhängig von Konfigurationsschritten. In GitHub müssen beispielsweise bestimmte Einstellungen für CI/CD-Pipelines freigegeben werden [[12]]. Für Cursor bedeutet dies, dass der Agent korrekt mit GitHub und ggf. anderen Diensten verbunden ist [[165]]. **Positive Nachweis:** Nachdem ein OIDC-Anbieter in der Cloud konfiguriert und in GitHub als vertrauenswürdige Identität registriert wurde, können Workflows erfolgreich mit kurzlebigen Tokens authentifiziert werden [[253]]. **Negative Testfall:** Ein GitHub Action Workflow scheitert, weil das OIDC-Token nicht validiert werden kann, möglicherweise aufgrund einer falschen Konfiguration des Cloud-Anbieters [[253]]. **Blindstelle:** Die Notwendigkeit, mehrere externe Systeme (Cloud-Anbieter, GitHub, Cursor) korrekt zu konfigurieren, birgt viele Potenzial für Fehler. **Abbruchbedingung:** Ein fehlschlagender Health Check in der Duo-Integration könnte die gesamte Aktivierung verhindern [[336]].

**`CONFIGURED`:** Dieses Glied ist entscheidend, da es die tatsächliche Einstellung der Systeme untersucht. Eine gute Konfiguration ist oft schwerer zu erreichen als die bloße Aktivierung. **Architektur A:** Die Konfiguration von GitLab Runner ist ein bekannter Schmerzpunkt. Sie erfolgt manuell über die Datei `config.toml` [[342]], und Fehler in dieser Datei können die Sicherheit erheblich beeinträchtigen [[234]]. Es gibt verschiedene Executor-Typen (z.B. Shell, Docker), deren richtige Isolation gewährleistet werden muss [[341]]. Die Konfiguration von Duo erfordert genaue Netzwerkkonnektivitätsvorgaben [[225]]. **Positive Nachweis:** Ein GitLab Runner, der korrekt mit der Instanz verbunden ist und eine einfache Job-Schritt ausführt [[427]]. **Negative Testfall:** Ein Runner, der aufgrund einer falschen `allowed_pull_policies`-Einstellung nicht die richtigen Container-Images pullen kann [[221]]. **Blindstelle:** Die Notwendigkeit, sowohl die GitLab-Instanz als auch den Duo-Service zu konfigurieren, führt zu einer hohen Komplexität. Die Konfiguration der Runner-Arbeitslasten kann ebenfalls komplex sein, insbesondere in Kubernetes-Umgebungen, wo ganze Pod-Spezifikationen angepasst werden können [[220]]. **Abbruchbedingung:** Ein unzureichender Speicherplatz auf dem Runner-Host führt dazu, dass Jobs nicht ausgeführt werden können [[226]]. **Architektur B:** Die Konfiguration ist ebenfalls anspruchsvoll, aber die zugrundeliegenden Technologien sind oft standardisierter. Die Konfiguration von Cursor beinhaltet das Setzen von API-Schlüsseln und die Definition von Regeln [[64,255]]. Die größte Herausforderung liegt in der Einrichtung von OIDC für GitHub, was eine genaue Konfiguration in der Cloud (AWS, Azure, GCP) erfordert, um GitHub als vertrauenswürdigen Identitätsanbieter zu registrieren [[253,381]]. **Positive Nachweis:** Ein Cursor-Agent, der erfolgreich eine GitHub-Repository-Liste anzeigt, nachdem die MCP-Konfiguration mit einem Token vorgenommen wurde [[158]]. **Negative Testfall:** Ein Cursor-Agent, der versucht, eine Datei zu pushen, aber auf eine Sandbox-Beschränkung trifft, die nicht korrekt behandelt wird [[394]]. **Blindstelle:** Die Sandbox-Funktionalität von Cursor ist zwar ein wichtiges Sicherheitsmerkmal, wird aber in vielen Berichten als instabil und fehleranfällig beschrieben, was die Konfiguration erschwert [[397,398]]. **Abbruchbedingung:** Ein fehlerhaftes OIDC-Zertifikat oder eine falsche IAM-Rolle in der Cloud führt zu einer nicht lösbaren Authentifizierungsproblematik.

## Validierung der Claim-Kette: KONFIGURIERT bis AUSGEFÜHRT

Nachdem die grundlegenden Voraussetzungen `EXISTS` bis `ENABLED` überprüft wurden, folgt die nächste Sequenz der Claim-Kette: `CONFIGURED`, `EXECUTED`, `RECEIPT-VERIFIED`, `INDEPENDENCE-QUALIFIED` und `AXIOM-ADJUDICATED`. Diese Phasen sind entscheidend, da sie die eigentliche Funktionalität, die Qualität der generierten Beweise und die Unabhängigkeit der Entscheidungsfindung testen. Die Architekturen werden hier an ihren Grenzen getestet, und die Unterschiede in ihrem Design werden besonders deutlich. Die Analyse muss für jedes Glied einen positiven Nachweis, einen negativen Testfall, eine dokumentierte Blindstelle und eine klare Abbruchbedingung liefern [[1]].

**`CONFIGURED`:** Dieses Glied prüft, ob die Systeme so eingerichtet werden können, dass sie sicher und gemäß den Richtlinien arbeiten. **Architektur A (GitLab-Duo-MCP):** Die Konfiguration von GitLab Runner ist ein kritisches Feld. Administratoren müssen sicherstellen, dass die Isolation der Arbeitsumgebungen gewährleistet ist, sei es durch VMs, Docker-Containern oder anderen Methoden [[76]]. Die Konfigurationsdatei `config.toml` ist zentral, aber fehleranfällig [[342]]. Es gibt fortgeschrittene Optionen wie die Übersteuerung von Pod-Spezifikationen in Kubernetes, was Flexibilität bietet, aber auch die Komplexität erhöht [[220]]. Die Konfiguration von GitLab Duo ist ebenfalls anspruchsvoll und erfordert genaue Netzwerkregeln, um eine Kommunikation mit dem Duo-Service herzustellen [[225]]. **Positive Nachweis:** Eine GitLab Runner-Instanz, die in einer dedizierten Kubernetes-Pod-Umgebung läuft und isolierte Jobs ausführt [[348]]. **Negative Testfall:** Ein Job, der versucht, sensible Daten aus der Runner-Umgebung herauszuschreiben, weil die Isolation nicht korrekt konfiguriert war. **Blindstelle:** Die Abhängigkeit von der manuellen Konfiguration der `config.toml`-Datei ist eine große Schwachstelle. Änderungen müssen oft manuell per HUP-Signal neu geladen werden, was fehleranfällig ist [[232,235]]. **Abbruchbedingung:** Ein Konfigurationsfehler, der dazu führt, dass der Runner sich nicht mehr mit der GitLab-Instanz verbinden kann, blockiert alle CI/CD-Prozesse. **Architektur B (AXIOM-Cursor-GitHub):** Die Konfiguration hier ist stärker auf Protokollen wie OIDC und MCP basiert. Die Sicherheit von Cursor hängt stark von der korrekten Konfiguration seiner Regeln und der Deaktivierung riskanter Modi wie Auto-Run ab [[8,504]]. Die Konfiguration der Sandbox ist ebenfalls entscheidend, aber wie bereits erwähnt, problematisch. **Positive Nachweis:** Ein Cursor-Agent, der mit dem Parameter `--headless` in einem GitHub Action Workflow läuft, um Build-Fehler zu beheben, was eine headless-Konfiguration demonstriert [[143]]. **Negative Testfall:** Ein Cursor-Agent, der automatisch eine `.env`-Datei liest und sensible Informationen preisgibt, weil die Sicherheitsregeln dafür nicht konfiguriert wurden. **Blindstelle:** Die Sandbox-Funktionalität ist zwar ein Ziel, aber in der Praxis oft nicht zuverlässig, was die Konfiguration schwierig macht [[398]]. **Abbruchbedingung:** Wenn die Sandbox vollständig deaktiviert wird, um Probleme zu umgehen, wird die Sicherheitsarchitektur des Systems fundamental untergraben.

**`EXECUTED`:** Dieses Glied validiert, ob die Systeme ihre Aufgaben tatsächlich und gemäß der Konfiguration ausführen können. **Architektur A:** GitLab Runner ist dafür konzipiert, Aufgaben in CI/CD-Pipelines auszuführen [[69]]. Die Ausführung kann durch Sicherheitsrichtlinien wie Scan-Execution-Policies gesteuert werden, die sicherstellen sollen, dass bestimmte Scans durchgeführt werden [[74]]. **Positive Nachweis:** Ein CI/CD-Pipeline, die eine Anwendung kompiliert, Tests ausführt und ein Container-Image erstellt. **Negative Testfall:** Eine Pipeline, die fehlschlägt, weil eine erforderliche Sicherheitsscannings-Richtlinie nicht erfüllt wurde. **Blindstelle:** Die Richtlinien überprüfen oft nur die Konfiguration, nicht die tatsächliche Ausführung, was eine Lücke darstellt [[272]]. **Abbruchbedingung:** Ein Runner-Prozess, der aufhört, Jobs zu empfangen, weil er nicht mehr authentifiziert werden kann, typischerweise nach Änderungen an den 2FA-Einstellungen [[35]]. **Architektur B:** Die Ausführung erfolgt durch den Cursor-Agenten, der Skripte, API-Aufrufe oder andere Aktionen ausführt. Die Ausführung findet in einer Sandboxumgebung statt, die jedoch als instabil gilt [[398]]. **Positive Nachweis:** Ein Cursor-Agent, der eine PR-Erstellung und die Hinzufügung von Labels in GitHub erfolgreich automatisiert [[68]]. **Negative Testfall:** Ein Agent, der versucht, einen Befehl im Terminal auszuführen, der aufgrund von Sandbox-Beschränkungen fehlschlägt, und das Problem nicht automatisch löst [[397]]. **Blindstelle:** Die inhärente Instabilität der Sandbox kann dazu führen, dass wichtige Aktionen nicht ausgeführt werden können, selbst wenn sie logisch korrekt sind. Dies ist eine fundamentale Schwäche der Architektur. **Abbruchbedingung:** Ein Agent, der in einer Endlosschleife von Sandbox-Fehlern stecken bleibt und nie seine Hauptaufgabe erledigt.

**`RECEIPT-VERIFIED`:** Dies ist ein kritisches Glied, das die Fähigkeit der Architektur testet, fälschungssichere Beweise für ihre Aktionen zu generieren und zu verifizieren. **Architektur A:** Die Provenienz wird indirekt über Konzepte wie SLSA angestrebt, die von GitHub Actions unterstützt werden [[14,137]]. Wenn ein GitLab Runner auf einem GitHub-hosted Runner läuft, können SLSA Attestationen generiert werden. Die Verifizierung dieser Attestationen ist jedoch ein externer Prozess, der spezielle Werkzeuge wie `slsa-verifier` erfordert [[133]]. Die Attestationen werden typischerweise von GitHub selbst erzeugt, nicht von GitLab [[133]]. **Positive Nachweis:** Ein Artefakt, das mit einem gültigen SLSA Provenance Attestation versehen ist, das von einem externen Tool erfolgreich verifiziert wurde [[474]]. **Negative Testfall:** Ein Artefakt, das mit einer manipulierten oder fehlenden Attestation veröffentlicht wird, die von der Verifizierungslogik erkannt wird. **Blindstelle:** Die Architektur ist stark von externen Diensten (GitHub Actions) abhängig, um Provenienzbeweise zu generieren. Ohne diesen Zusammenschluss wäre die native Fähigkeit von GitLab, fälschungssichere Beweise zu liefern, begrenzt. **Abbruchbedingung:** Die Unfähigkeit, die Signatur der Attestation zu verifizieren, führt zum Scheitern der Überprüfung. **Architektur B:** Hier liegt der entscheidende Vorteil. GitHub unterstützt seit neuestem OIDC-Tokens mit immutablen Subject Claims [[163]]. Dies bedeutet, dass jedes Mal, wenn ein Agent (z.B. in Cursor) eine Aktion in GitHub initiiert (z.B. ein Commit), ein JWT-Token ausgestellt wird, das die Identität des initiierenden Benutzers, die Zeit und andere Attribute auf unbestreitbare Weise enthält. Diese Tokens können von Cloud-Anbietern oder anderen Diensten kryptografisch verifiziert werden [[378]]. **Positive Nachweis:** Ein Agent, der einen Commit in GitHub erstellt, der mit einem OIDC-Token signiert ist, das von AWS, Azure oder GCP als legitim verifiziert wird, um eine Rolle zu assumieren. **Negative Testfall:** Ein Versuch, einen Commit mit einem manipulierten OIDC-Token zu erstellen, der bei der Verifizierung durch den Empfänger fehlschlägt. **Blindstelle:** Die Abhängigkeit von der korrekten Konfiguration des OIDC-Anbieters in der Cloud. Ein einziger Fehler dort macht das ganze System unbrauchbar. **Abbruchbedingung:** Der Widerruf der Berechtigung des OIDC-Anbieters in der Cloud führt dazu, dass neue Tokens nicht mehr ausgestellt oder verifiziert werden können.

**`INDEPENDENCE-QUALIFIED`:** Dieses Glied prüft, ob die Entscheidungen der Architekturen wirklich unabhängig getroffen werden oder ob sie von den zugrundeliegenden Plattformen diktiert sind. **Architektur A:** Die Entscheidungen sind stark von GitLab und Duo abhängig. Die Composite Identity ist eine Logik, die von GitLab implementiert wird, um die Identität des Agenten plausibel der menschlichen Benutzer zuzuordnen [[205]]. Die Entscheidung, ob ein Runner eine Aufgabe ausführt, wird von GitLab getroffen. Die Unabhängigkeit ist daher gering. **Positive Nachweis:** Ein Agent, der auf Basis seiner internen Logik eine Entscheidung trifft, die nicht direkt von einer GitLab-API-Antwort abhängt. **Negative Testfall:** Ein Agent, der ausschließlich Befehle ausführt, die ihm direkt über GitLab CI/CD Variablen vorgegeben werden. **Blindstelle:** Es ist schwer zu beweisen, dass ein Agent handelt, weil er es will, und nicht, weil GitLab es ihm sagt. **Abbruchbedingung:** Die Abschaltung des GitLab-Servers führt zum sofortigen Stillstand aller Agentenaktivitäten. **Architektur B:** Auch hier ist eine Abhängigkeit gegeben, aber die Protokolle bieten mehr Potenzial für Unabhängigkeit. Die Entscheidung des Cursor-Agents wird durch seine interne Regelengine und sein Training beeinflusst [[255]]. Die Verifizierung der Aktionen findet über OIDC statt, was eine Verbindung zur zugrundeliegenden Identitätsplattform GitHub herstellt [[163]]. **Positive Nachweis:** Ein Agent, der auf Basis seiner Regeln eine Sicherheitslücke in einem Repository findet und einen Pull Request zur Korrektur erstellt, ohne dass eine externe Triggeraktion dazu notwendig war. **Negative Testfall:** Ein Agent, der nur auf Befehle reagiert, die ihm über die Cursor-Schnittstelle erteilt werden. **Blindstelle:** Die Unabhängigkeit ist weiterhin limitiert durch die Abhängigkeit von der Cursor-IDE und der GitHub-Plattform. Die Provider-Trennung ist nicht automatisch gegeben <user>. **Abbruchbedingung:** Die Deaktivierung der MCP-Schnittstelle in Axiom würde die Fähigkeit des Agents untergraben, auf komplexe Daten zuzugreifen.

**`AXIOM-ADJUDICATED`:** Dies ist das finale Glied der Kette, das die adäquate Behandlung von Ansprüchen durch die Architektur testet. **Architektur A:** Es gibt keine native Unterstützung für eine Adjudikation innerhalb dieser Architekturgruppe. Die Adjudikation müsste als externer Prozess implementiert werden, der die Audit-Logs von GitLab analysiert [[173]]. **Positive Nachweis:** Ein externer Prozess, der die GitLab-Logs liest und feststellt, dass alle Aktionen gemäß den definierten Sicherheitsrichtlinien durchgeführt wurden. **Negative Testfall:** Ein externer Prozess, der einen unberechtigten Zugriffsversuch in den Logs entdeckt. **Blindstelle:** Die Architektur ist nicht für die Adjudikation konzipiert. Sie ist primär für die Ausführung von Aufgaben. **Abbruchbedingung:** Die Unfähigkeit, eine adäquate Auditspur zu erhalten, macht eine formale Adjudikation unmöglich. **Architektur B:** Dies ist ein Kernfeature der Architektur. Axiom wurde entwickelt, um Daten zu analysieren, und sein MCP-Server ist explizit dafür konzipiert, Agenten den Zugriff auf Daten zu ermöglichen [[292,294]]. Die Architektur ist also nativ auf die Generierung von Beweisen und deren potenzielle Adjudikation durch Axiom ausgelegt. **Positive Nachweis:** Ein Axiom MCP-Server, der von einem Cursor-Agenten verwendet wird, um eine komplexe Datenanfrage zu stellen und die Ergebnisse zu erhalten [[296]]. **Negative Testfall:** Ein Agent, der versucht, eine Datenabfrage zu stellen, die über seine Berechtigungen hinausgeht, und der MCP-Server lehnt die Anfrage auf Basis der Regeln von Axiom ab. **Blindstelle:** Die Effektivität der Adjudikation hängt von der Qualität der Regeln und Datenmodelle in Axiom ab. **Abbruchbedingung:** Ein systemweiter Ausfall des Axiom-Dienstes würde die adäquate Behandlung von Ansprüchen, die auf Axiom-Daten basieren, unmöglich machen.

## Validierung der Claim-Kette: BEWEIS-BESTÄTIGT bis ADJUDIKATION-ABGESCHLOSSEN

Die letzte Sequenz der Claim-Kette – `RECEIPT-VERIFIED`, `INDEPENDENCE-QUALIFIED`, `AXIOM-ADJUDICATED` – bildet den Höhepunkt der Untersuchung. Sie testet die Fähigkeit der Architekturen, nicht nur Aktionen auszuführen, sondern diese Aktionen in einem fälschungssicheren, unabhängigen und nachprüfbar-weisen Prozess zu verankern und zu bewerten. Diese Phasen sind von entscheidender Bedeutung für die Vertrauenswürdigkeit agenter Systeme. Die Analyse dieser Glieder offenbart die fundamentalen Design-Philosophien der beiden Architekturen am deutlichsten.

**`RECEIPT-VERIFIED`:** Dieses Glied fordert die Architekturen auf, ihre Fähigkeit zur Generierung und Verifikation von Beweisen unter Beweis zu stellen. **Architektur A (GitLab-Duo-MCP):** Wie in der vorherigen Analyse dargelegt, ist die Provenienz hier eine indirekte Angelegenheit. Die Architektur greift auf Standards wie SLSA (Supply-chain Levels for Software Artifacts) zurück, die von GitHub Actions unterstützt werden [[137,238]]. Wenn CI/CD-Jobs auf einem GitLab Runner laufen, der Teil einer GitHub-Infrastruktur ist, können SLSA-Provenienz-Attestationen für erstellte Artefakte generiert werden [[14]]. Diese Attestationen sind kryptografisch signierte Metadaten, die die Herkunft des Artefakts belegen [[140]]. Die Verifizierung dieser Attestationen ist jedoch kein integrierter Prozess. Sie erfordert externe Werkzeuge wie `slsa-verifier` [[133]] und setzt voraus, dass die Attestationen korrekt generiert und gepusht werden [[237]]. Ein wesentlicher Mangel ist, dass GitLab selbst nicht als Generator solcher Attestationen für seine eigenen Artefakte dokumentiert ist; die Quelle ist meistens GitHub [[133]]. Dies schafft eine Abhängigkeit und eine potenzielle Blindstelle. **Positive Nachweis:** Ein Container-Image, das mit einem gültigen SLSA Level 3 Provenance Attestation versehen ist, das von einem externen Skript erfolgreich gegen den entsprechenden Build-Prozess und die Quellcode-Revision verifiziert wird [[474]]. **Negative Testfall:** Ein Versuch, ein Artefakt mit einer manipulierten oder fehlenden Attestation zu veröffentlichen, der von der Verifizierungslogik als ungültig markiert wird. **Blindstelle:** Die Abhängigkeit von externen Diensten (insbesondere GitHub Actions) für die Erzeugung fälschungssicherer Beweise ist eine Schwachstelle. Ohne diese Verbindung ist die native Fähigkeit von GitLab, unbestechliche Beweise zu produzieren, stark eingeschränkt. **Abbruchbedingung:** Die Unfähigkeit, die digitale Signatur der Attestation zu validieren, führt zum Abbruch des Verifikationsprozesses. **Architektur B (AXIOM-Cursor-GitHub):** Diese Architektur bietet hier einen qualitativ hochwertigeren Ansatz. Der Schlüssel liegt in der Verwendung von OpenID Connect (OIDC) in Kombination mit immutablen Subjekt-Ansprüchen, die von GitHub eingeführt wurden [[163]]. Jede Aktion, die von einem Agenten initiiert wird, der über OIDC authentifiziert ist (z.B. ein Commit, ein Push, ein Deploy), kann mit einem JSON Web Token (JWT) versehen werden. Dieses JWT enthält nicht veränderbare Ansprüche wie die Identität des Benutzers (`sub`-Anspruch), die Organisation, den Zeitstempel und weitere kontextbezogene Informationen [[403]]. Da das Token von einer vertrauenswürdigen Quelle (GitHub) ausgestellt wird und kryptografisch signiert ist, kann es von jedem Partner (z.B. ein Cloud-Anbieter) verifiziert werden, ohne dass ein vertrauenswürdiger Kanal zwischen Agent und Partner benötigt wird [[378]]. Dies ist ein weitaus robusterer und nativer Mechanismus zur Beweisverifikation als die Anwendung externer Standards wie SLSA. Ergänzt wird dies durch Konzepte wie "issuer-blind receipt verification", bei denen jede Antwort eines Modells mit einer digitalen Signatur versehen wird, die offline verifiziert werden kann, ohne dass ein Account oder eine API-Verbindung zum Modellanbieter nötig ist [[150,240]]. **Positive Nachweis:** Ein Cursor-Agent, der eine Aktion in GitHub ausführt, die mit einem OIDC-Token signiert wird. Ein Cloud-Workflow in AWS oder Azure kann dieses Token empfangen, verifizieren und die Identität des Initiators sicher bestätigen, um eine Berechtigung zu erteilen. **Negative Testfall:** Ein Angreifer versucht, einen OIDC-Token zu erstellen, der die Identität eines anderen Benutzers vortäuscht. Die Verifizierungslogik des Cloud-Anbieters erkennt die Ungültigkeit und blockiert die Aktion. **Blindstelle:** Die gesamte Sicherheit dieses Mechanismus hängt von der korrekten Konfiguration des OIDC-Anbieters in der Cloud ab. Ein einziger Fehler in den Vertrauensbeziehungen (Trust Relationships) macht die fälschungssichere Identifikation unmöglich. **Abbruchbedingung:** Die Widerrufung der OIDC-Anbindung zwischen GitHub und dem Cloud-Anbieter führt dazu, dass neue gültige Tokens nicht mehr ausgestellt oder verifiziert werden können.

**`INDEPENDENCE-QUALIFIED`:** Dieses Glied ist hochgradig analytisch und prüft, ob die Entscheidungen der Architekturen autonom getroffen werden oder ob sie von der zugrundeliegenden Plattform diktiert sind. Die Quellen betonen explizit, dass eine Trennung der Anbieter nicht automatisch eine Unabhängigkeit der Modelle, Scanner oder Regelsätze impliziert <user>. **Architektur A:** Die Entscheidungsfindung ist tief in die GitLab-Plattform integriert. Die Composite Identity, ein Kernmerkmal von GitLab Duo, ist eine Logik, die von GitLab implementiert wird, um sicherzustellen, dass die Aktivitäten, die ein Agent im Namen eines Benutzers ausführt, als Teil seiner Identität betrachtet werden und keine separaten Privilegien erhalten [[205]]. Die Entscheidung, ob ein CI/CD-Job überhaupt ausgeführt wird, trifft GitLab basierend auf der Konfiguration des Runners und den Berechtigungen des Benutzers. Der Agent operiert innerhalb des von GitLab definierten Rahmens. Die Unabhängigkeit ist somit inhärent gering. **Positive Nachweis:** Ein GitLab Duo Agent, der eine Codeüberprüfung durchführt und auf Basis seines Trainings und der Regeln eine Verbesserungsvorschlag macht, der über die einfachen Syntax-Checks hinausgeht. **Negative Testfall:** Ein Agent, der ausschließlich Befehle ausführt, die ihm direkt über die `.gitlab-ci.yml`-Konfiguration oder als Kommentar in einer Merge Request vorgegeben werden. **Blindstelle:** Es ist extrem schwierig, zu beweisen, dass ein Agent handelt, weil er es für richtig hält, und nicht, weil GitLab es ihm vorschreibt. Die Metrik `Unabhängigkeitsvektor` für diese Architektur wäre wahrscheinlich niedrig. **Abbruchbedingung:** Der vollständige Ausfall der GitLab-Instanz führt zum sofortigen Stillstand aller Agentenaktivitäten und -entscheidungen. **Architektur B:** Auch hier ist eine Abhängigkeit von den Plattformen gegeben, aber die Protokolle bieten mehr Potenzial für eine scheinbare Unabhängigkeit. Der Cursor Agent trifft seine Entscheidungen auf Basis seines internen Modells, seiner Programmierlogik und einer Sammlung von Regeln, die in der IDE definiert sind [[255]]. Die Ausführung der Aktionen findet über eine Sandbox statt, die eine gewisse Isolation bietet [[395]]. Die Verifizierung der Aktionen erfolgt über OIDC, was eine Verbindung zur zugrundeliegenden Identitätsplattform GitHub herstellt [[163]]. **Positive Nachweis:** Ein Cursor Agent, der eine komplexe Aufgabe selbstständig zerlegt, für jeden Teil eine Lösung findet und diese zusammenfügt, um ein endgültiges Ergebnis zu liefern, ohne dass ein menschlicher Operator eingreifen muss. **Negative Testfall:** Ein Agent, der nur auf direkte Befehle über die grafische Benutzeroberfläche von Cursor reagiert und keine proaktiven Aktionen unternimmt. **Blindstelle:** Die Unabhängigkeit ist weiterhin limitiert durch die Abhängigkeit von der Cursor-IDE und der GitHub-Plattform. Die Sandbox-Funktionalität ist zwar ein Schritt in die richtige Richtung, wird aber in der Praxis als instabil beschrieben, was die Planbarkeit und damit die Unabhängigkeit der Agenten beeinträchtigt [[398]]. **Abbruchbedingung:** Die Deaktivierung der MCP-Schnittstelle in Axiom würde die Fähigkeit des Agents untergraben, auf komplexe externe Daten zuzugreifen, was seine Autonomie stark einschränkt.

**`AXIOM-ADJUDICATED`:** Dies ist das finale Glied, das die Fähigkeit der Architektur zur formalen Beurteilung von Behauptungen testet. **Architektur A:** Diese Architekturgruppe ist nicht für die Adjudikation konzipiert. Es gibt keine integrierte Komponente, die auf Basis der generierten Beweise eine formale Entscheidung trifft. Die Adjudikation müsste als separate, externe Anwendung realisiert werden, die beispielsweise die Audit-Logs von GitLab analysiert [[173]] und gegen eine Reihe von Regeln prüft. Dies ist eine passive und reaktive Methode, keine native Funktion. **Positive Nachweis:** Ein externer Prozess, der periodisch die GitLab-Logs abfragt, eine ungewöhnliche Aktivität (z.B. ein massiver Datenexport) erfasst und eine Warnung auslöst. **Negative Testfall:** Ein externer Prozess, der einen bekannten Angriffsweg in den Logs nachweist, der trotz vorhandener Sicherheitsrichtlinien nicht blockiert wurde. **Blindstelle:** Die Architektur ist primär auf die Ausführung von Aufgaben (CI/CD, Code-Assistenz) ausgelegt, nicht auf die Überwachung und Bewertung dieser Ausführungen. **Abbruchbedingung:** Die Unfähigkeit, eine auditable Spur der Ereignisse zu hinterlassen, macht eine formale Adjudikation prinzipiell unmöglich. **Architektur B:** Diese Architektur ist explizit darauf ausgelegt, Ansprüche zu verarbeiten und zu bewerten. Axiom ist eine Plattform für maschinelles Datenobservabilität und -analyse [[293]]. Sein MCP-Server ist eine spezifische Implementierung, die es Agenten ermöglicht, Axiom Processing Language (APL)-Abfragen direkt auszuführen [[294,297]]. Wenn ein Agent einen Anspruch formuliert (z.B. "Finde alle Sicherheitslücken in diesem Projekt"), kann Axiom diesen Anspruch verstehen, die relevanten Datenquellen (Logdaten, Code, CI/CD-Ereignisse) analysieren und ein Ergebnis liefern. Dies ist ein aktiver, proaktiver Adjudikationsprozess. Die Architektur ist also von Grund auf für die Behandlung von Anfragen und die Bereitstellung von Beweisen für diese Anfragen konzipiert. **Positive Nachweis:** Ein Cursor-Agent, der eine APL-Abfrage an den Axiom MCP-Server sendet, um die Ursache eines Fehlers in einer Pipeline zu diagnostizieren. Der Server analysiert die Daten und liefert eine präzise Antwort mit den relevanten Log-Einträgen und Zeilennummern [[296]]. **Negative Testfall:** Ein Agent, der eine Anfrage stellt, die syntaktisch falsch ist oder auf Daten zugreift, für die er keine Berechtigung hat. Der Axiom MCP-Server lehnt die Anfrage auf Basis seiner Sicherheitsrichtlinien ab und gibt einen Fehler zurück. **Blindstelle:** Die Qualität der Adjudikation hängt direkt von der Qualität der Daten in Axiom und der Komplexität der APL-Abfragen ab. Es besteht die Gefahr der "Context Saturation", bei der der Agent relevante Informationen aus einer großen Menge von Daten nicht mehr extrahieren kann [[289]]. **Abbruchbedingung:** Ein systemweiter Ausfall des Axiom-Dienstes würde die adäquate Behandlung von Ansprüchen, die auf Axiom-basierten Datenanalysen beruhen, unmöglich machen.

## Vektormetrische Synthese und Unabhängigkeitsanalyse

Nachdem jede Phase der Claim-Kette detailliert analysiert wurde, ist es nun möglich, die Erkenntnisse in eine strukturierte, quantitative Form zu bringen, indem wir die geforderten Vektormetriken anwenden. Diese Metriken ermöglichen einen vergleichenden Blick auf die Stärken und Schwächen der Architekturen, ohne auf synthetische Gesamt-Trust-Scores zurückzugreifen <user>. Die Analyse konzentriert sich auf fünf Kernmetriken: `Claim-Chain-Coverage`, `Receipt-Vollständigkeit`, `Subject-Binding`, `Provider-Origin-Integrität` und den `Unabhängigkeitsvektor`.

**Claim-Chain-Coverage:** Diese Metrik misst, wie viele Glieder der Claim-Kette `EXISTS → ENTITLED → ENABLED → CONFIGURED → EXECUTED → RECEIPT-VERIFIED → INDEPENDENCE-QUALIFIED → AXIOM-ADJUDICATED` von einer Architektur in einem plausiblen und funktionalen Rahmen erfüllt werden können. Ein ideales System würde alle 8 Glieder mit positiven Nachweisen, dokumentierten Abbruchbedingungen und minimalem Blindspot-Status abdecken.

*   **Architektur A (GitLab-Duo-MCP):** Die Deckung ist in den frühen Phasen (`EXISTS`, `ENTITLED`, `ENABLED`) sehr hoch. Die Architektur ist für die Bereitstellung von Plattformen und die Verwaltung von Berechtigungen konzipiert. Bei `CONFIGURED` und `EXECUTED` sinkt die Deckung leicht aufgrund der bekannten Komplexität und Fehleranfälligkeit der Konfiguration von GitLab Runner und der fragilen Natur von GitLab Duo [[76,206]]. Die größte Schwäche liegt bei `RECEIPT-VERIFIED`. Die Abhängigkeit von externen Diensten wie GitHub für die Generierung fälschungssicherer Beweise (SLSA) ist eine signifikante Lücke [[133,137]]. `INDEPENDENCE-QUALIFIED` und `AXIOM-ADJUDICATED` sind praktisch nicht vorhanden, da die Architektur nicht für diese hochspezialisierten Aufgaben konzipiert ist. Die `Claim-Chain-Coverage` ist daher für Architektur A moderat bis niedrig, mit starken Schwächen in den späteren Phasen der Kette.
*   **Architektur B (AXIOM-Cursor-GitHub):** Die Deckung ist ebenfalls hoch in den frühen Phasen. Die Architektur ist modern und auf die Bereitstellung von Diensten über Protokolle wie OIDC ausgelegt. Die größte Stärke ist die Deckung von `RECEIPT-VERIFIED`. Die Verwendung von OIDC mit immutablen Subject Claims in GitHub bietet einen nativen, kryptografisch starken Mechanismus zur Generierung von Beweisen, der der Architektur inhärent ist [[163]]. Dies hebt die Architektur deutlich von Architektur A ab. `AXIOM-ADJUDICATED` ist ein Kernmerkmal, da Axiom explizit als Adjudikations- und Analyseplattform konzipiert ist [[292]]. Die Schwäche liegt in `EXECUTED`, wo die Instabilität der Cursor-Sandbox eine negative Testfall-Eigenschaft darstellt [[398]]. `INDEPENDENCE-QUALIFIED` ist ebenfalls eine Schwäche, da die Agenten stark von der Cursor-IDE und der GitHub-Plattform abhängen. Dennoch ist die overall `Claim-Chain-Coverage` für Architektur B höher als für Architektur A, insbesondere dank der robusten Provenienzfähigkeiten und der nativen Adjudikationsfähigkeit.

**Receipt-Vollständigkeit:** Diese Metrik beurteilt die Qualität und Unabhängigkeit der generierten Beweise. Sie ist untrennbar mit der Qualität des `Subject-Bindings` verknüpft.

*   **Architektur A:** Die Vollständigkeit ist unvollständig. Die Beweise (SLSA Attestationen) sind zwar formal korrekt, aber sie sind fragmentiert und erfordern externe Systeme und Werkzeuge für ihre Erstellung und Verifikation. Die Verbindung zwischen der Handlung und dem handelnden Subjekt (der Agent) ist weniger direkt als bei Architektur B. Die Beweise sind eher Eigenschaften der Artefakte als der Agentenaktionen selbst.
*   **Architektur B:** Die Vollständigkeit ist hoch. Die Beweise (OIDC-Tokens) sind integraler Bestandteil jeder Aktion des Agenten. Sie sind zeitnah, kontextbezogen und kryptografisch unbestreitbar. Sie binden die Aktion direkt an den identifizierten Benutzer und das System, das sie initiiert hat. Dies erzeugt ein vollständiges und unaufdringliches Bild der Ereignisse.

**Subject-Binding:** Diese Metrik prüft, wie sicher die Identität des Akteurs (Mensch oder Agent) mit seiner Handlung verknüpft ist.

*   **Architektur A:** Die Bindung ist mittelmäßig. Die Composite Identity von GitLab Duo ist ein Versuch, die Aktivitäten des Agenten der zugrundeliegenden menschlichen Identität zuzuordnen [[205]]. Dies ist jedoch eine Logik-basierte Zuordnung, die potenziell umgangen oder fehlerhaft konfiguriert werden kann [[206]]. Die Bindung ist nicht kryptografisch verifizierbar.
*   **Architektur B:** Die Bindung ist hoch. Die Verwendung von OIDC mit immutablen Subject Claims schafft eine kryptografisch gesicherte, unbestreitbare Verbindung zwischen der handelnden Identität und der Aktion [[163]]. Ein Verifizierer kann die Identität des Initiators ohne Rückfrage bei einer zentralen Autorität bestätigen, was eine starke und unabhängige Bindung darstellt.

**Provider-Origin-Integrität:** Diese Metrik bewertet, wie stark die Architektur von einem einzelnen Anbieter abhängig ist und wie gut die Integrität der Daten und Dienste gewährleistet ist.

*   **Architektur A:** Die Integrität ist moderat. Die Architektur ist stark an das GitLab-Ökosystem gebunden. Die Abhängigkeit von externen Diensten wie Duo für zentrale Funktionen wie MFA ist eine Schwachstelle. Die Abhängigkeit von externen Tools für die Beweisverifikation (SLSA) reduziert die Eigenständigkeit.
*   **Architektur B:** Die Integrität ist hoch. Obwohl die Architektur auf drei großen Plattformen basiert (Axiom, Cursor, GitHub), kommunizieren diese über offene Standards wie MCP und OIDC. Dies ermöglicht eine modulare Struktur, bei der die Komponenten austauschbar sind. Die Verwendung von Standardprotokollen reduziert die Abhängigkeit von proprietären APIs und verbessert die Interoperabilität und Resilienz der Gesamtlösung.

**Unabhängigkeitsvektor:** Diese Metrik versucht, die Autonomie der Agenten zu quantifizieren.

*   **Architektur A:** Der Vektor ist gering. Die Entscheidungen der Agenten finden innerhalb der strengen Regeln und des Rahmens der GitLab-Plattform statt. Die Composite Identity und die CI/CD-Pipelines definieren klare Grenzen für das Handeln des Agenten. Die Unabhängigkeit ist eher eine Illusion, da die Plattform die Kontrolle behält.
*   **Architektur B:** Der Vektor ist moderat bis hoch. Die Entscheidungen treffen die Agenten basierend auf ihren internen Regeln und ihrer Programmierung [[255]]. Die Sandbox bietet eine Form der Ausführungsumgebung, die von der primären IDE getrennt ist. Allerdings ist ihre Autonomie immer noch auf die Funktionalität der Cursor-IDE und die Berechtigungen in der GitHub-Organisation beschränkt. Die Instabilität der Sandbox kann die Planbarkeit und damit die wahrgenommene Unabhängigkeit beeinträchtigen [[398]].

Zusammenfassend lässt sich sagen, dass Architektur B mit ihren Metriken deutlich besser abschneidet, insbesondere in den kritischen Bereichen `Receipt-Vollständigkeit`, `Subject-Binding` und `Claim-Chain-Coverage`. Ihre reliance auf offene Standards schafft eine höhere `Provider-Origin-Integrität`. Architektur A ist robust in den klassischen DevOps-Bereichen, aber in den hochspezialisierten Anforderungen der Claim-Kette, insbesondere im Bereich der fälschungssicheren Provenienz und Adjudikation, deutlich unterlegen.

## Schlussfolgerungen und strategische Implikationen

Die umfassende, fälschungsoffene Untersuchung der beiden Architekturgruppen im Rahmen der vorgegebenen Claim-Kette führt zu klaren und differenzierten Ergebnissen. Weder Architektur A (GitLab Ultimate + Duo + MCP + Orbit) noch Architektur B (AXIOM + Cursor + GitHub) erweist sich als perfekt. Die Wahl zwischen ihnen hängt maßgeblich davon ab, welche Phasen der Claim-Kette für den spezifischen Anwendungsfall des Nutzers von höchster Priorität sind. Die Analyse, die strikt auf den bereitgestellten Quellen basiert und die expliziten Anforderungen an die Form der Ausgabe und die Bewertungsmethodik respektiert, zeigt eine klare Trennung der Stärken und Schwächen.

**Zusammenfassende Bewertung der Claim-Kette:**

Die Architektur B (AXIOM-Cursor-GitHub) zeigt sich als überlegen in den Phasen, die eine hohe Vertrauenswürdigkeit, Nachverfolgbarkeit und Unabhängigkeit erfordern. Ihr entscheidender Vorteil liegt in der `RECEIPT-VERIFIED`-Phase. Die Nutzung von OpenID Connect (OIDC) mit immutablen Subject Claims in GitHub schafft einen nativen, kryptografisch starken Mechanismus zur Generierung von fälschungssicheren Beweisen für jede Aktion eines Agenten [[163]]. Dies ist ein fundamental robusterer Ansatz als die indirekte und auf externe Dienste angewiesene Methode der Architektur A, die auf SLSA-Provenienz-Attestationen setzt [[133,137]]. Die Architektur B ist darüber hinaus für die finale Phase der Kette, `AXIOM-ADJUDICATED`, konzipiert. Die Integration eines MCP-Servers von Axiom ermöglicht eine native, proaktive Adjudikation von Anfragen und Problemdiagnosen, während Architektur A hierfür externe Logik erfordert [[292]]. Diese Stärken machen Architektur B ideal für Anwendungsfälle, in denen auditfähige und unbestreitbare Entscheidungsprozesse im Vordergrund stehen.

Architektur A (GitLab-Duo-MCP) ist in den früheren Phasen der Kette, `EXISTS`, `ENTITLED`, `ENABLED` und `CONFIGURED`, sehr solide und bietet eine etablierte Plattform für CI/CD und Identitätsmanagement. Die Governance über Konfiguration als Code und Scan-Ausführungsrichtlinien ist gut etabliert [[74,142]]. Ihre größten Schwächen manifestieren sich jedoch in den späteren Phasen. Die Abhängigkeit von externen Systemen für Provenienzbeweise ist eine signifikante Schwachstelle. Darüber hinaus ist die `INDEPENDENCE-QUALIFIED`-Phase schwach ausgeprägt, da die Agenten stark in die GitLab-Plattform integriert sind. Die Architektur A ist daher am besten für Anwendungsfälle geeignet, in denen die effiziente Ausführung von CI/CD-Pipelines und die Integration von AI-assistierten Entwicklungsprozessen in einem etablierten DevOps-Rahmen priorisiert werden.

**Strategische Implikationen für den Nutzer:**

Basierend auf dieser Analyse lassen sich folgende strategische Implikationen ableiten:

1.  **Priorisierung der Anforderungen:** Der Nutzer sollte zunächst seine Anforderungen an die Claim-Kette neu bewerten. Sind fälschungssichere Beweise (`RECEIPT-VERIFIED`) und eine native Adjudikationsfähigkeit (`AXIOM-ADJUDICATED`) kritische Anforderungen? Wenn ja, neigt Architektur B stark zu einem Vorteil. Sind stattdessen die Integrationsmöglichkeiten in bestehende CI/CD-Pipelines und die Verwaltung von Entwicklerwerkzeugen wichtiger, so bietet Architektur A eine solide Grundlage.

2.  **Akzeptanz der Komplexität:** Weder Architektur ist frei von Komplexität. Architektur A birgt Risiken in der fehleranfälligen Konfiguration von GitLab Runner und der fragilen Einrichtung von GitLab Duo [[76,206]]. Architektur B birgt Risiken in der komplexen Konfiguration für Enterprise Managed Authorization (EMA) über ID-JAG [[313]] und der bekannten Instabilität der Cursor-Sandbox [[398]]. Beide Architekturen erfordern ein hohes Maß an Expertise, um sicher und effektiv eingesetzt zu werden.

3.  **Handlungsempfehlung für die Implementierung:** Die Analyse hat gezeigt, dass keine Architektur vorab als "sicher" oder "unabhängig" bewertet werden darf, bis die acht prioritären Forschungsfährten abgeschlossen sind [[1]]. Daher ist der nächste Schritt, die Erkenntnisse dieser Untersuchung in eine praxisnahe Pilotphase zu übersetzen. Der Nutzer sollte:
    *   **Für Architektur A:** Ein Pilotprojekt starten, das die Konfiguration von GitLab Runner für maximale Isolation und die Einrichtung von GitLab Duo zur Composite Identity testet. Besonderes Augenmerk sollte auf der Identifizierung von Bypass-Pfaden und der Verifizierbarkeit von Beweisen gelegt werden.
    *   **Für Architektur B:** Ein Pilotprojekt starten, das die Konfiguration von OIDC in GitHub mit einem Cloud-Anbieter und die Entwicklung von Regeln für den Cursor-Agenten umfasst. Die Fähigkeit zur Blindvalidation sollte hierbei intensiv getestet werden, indem beispielsweise die Audit-Logs von GitHub gegen die Cursor-Regeln überwacht werden [[404]].

4.  **Langfristige Perspektive:** Die Analyse deutet darauf hin, dass Architektur B auf eine Zukunft zukünftiger agenter Systeme zugeschnitten ist, die auf offenen Protokollen und kryptografisch gesicherten Beweisen aufbauen. Architektur A ist eine leistungsfähige Evolution der aktuellen DevOps-Werkzeuge. Langfristig könnten die Prinzipien der Architektur B (Protokollorientierung, starke Identitätsbindung, native Adjudikation) an Bedeutung gewinnen. Investitionen in die Kompetenz für Architektur B könnten daher eine bessere Zukunftssicherung bieten.

Abschließend lässt sich festhalten, dass die vorliegende Untersuchung die beiden Architekturgruppen nicht nur vergleicht, sondern auch ein klares Bild davon zeichnet, wo ihre Stärken und Schwächen liegen. Die Entscheidung sollte nicht auf einer oberflächlichen Bewertung fallen, sondern auf den detaillierten, evidenzbasierten Ergebnissen dieser Analyse, die die spezifischen Anforderungen der Claim-Kette rigoros prüfen.
